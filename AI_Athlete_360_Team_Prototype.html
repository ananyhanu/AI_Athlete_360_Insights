What we are actually building

One Android + iOS app that walks a PE teacher through all 10 SAI battery fitness tests, records one video per test, measures the result on-device with computer vision, and prints a bilingual report card — with the phone in aeroplane mode. Everything else (dashboards, NSRS integration, analytics) is supporting cast.

The judging line from the Concept Note: build something that works in a dusty school ground, on a budget phone, held by a teacher who has never used an AI app. Every design argument gets settled by that sentence.

Non-negotiable 01

Offline-first, not offline-capable

Registration → 10 tests → measurement → report card → PDF, all with zero connectivity. Evaluators will physically switch on aeroplane mode and run 3 tests. No crash, no data loss.

Non-negotiable 02

On-device inference

No athlete video may touch Google Cloud, AWS, Azure, Colab, Drive or Dropbox — during development or the demo. Cloud LLM is allowed only on de-identified numeric scores for feedback text.

Non-negotiable 03

Consent + minors

Written parental consent for every under-18 we record while prototyping. DPDP Act 2023. Anonymised consent forms ship inside /compliance/.

Non-negotiable 04

Target device floor

Android 10, 3 GB RAM, 30 fps rear camera, no Play Services. 120 fps and NPU acceleration are bonuses, never requirements.

Non-negotiable 05

One video per test

Retakes allowed, but exactly 10 videos per athlete are retained. Auto-tag test name, athlete ID, timestamp, GPS. Reject <720p or out-of-duration clips at capture time.

Non-negotiable 06

Honest accuracy

No Indian dataset exists. We report our own measured error with sample size, devices and lighting — plus at least 3 documented failure cases. Inflated numbers lose more marks than modest ones.

The measurement pipeline, once

Every AI test runs through the same seven stages. Only stage 5 is test-specific — that's the whole point of the design and it's what we show the evaluators.

[1] CAPTURE camera session · 720p/30fps floor · duration + size gate · metadata injection | [2] PRE-FLIGHT lighting, angle, distance, single-subject, marker-visible checks → block or warn | [3] FRAME FEED decode → resize 256/640 → normalise → (optional) ROI crop | [4] POSE / DETECT MoveNet Thunder (INT8) or MediaPipe Pose · 33 landmarks + visibility | [5] TEST LOGIC ── state machine (sit-ups, shuttle) ──────────┐ ── event frames (jump, sprint) ───────────────┤ → raw measure ── homography scaling (height, broad, throw) ─┘ | [6] CONFIDENCE landmark visibility × frame consistency × fps × marker detected × occlusion | [7] RESULT value + unit + confidence band + "coach review" flag if below threshold

Confidence is a first-class output

Judges explicitly ask to see the detection, the measurement and the confidence. A number without a confidence band reads as overclaiming. Below threshold → the result is still saved, but flagged Needs coach review, and the coach can accept or re-record.

The calibration marker earns us bonus marks

Print an A4 sheet with a known-size ArUco/April tag. Detected in-frame, it fixes the pixel→cm scale for height, broad jump and throw. We must demo accuracy with and without it to prove it improves the number.

Sync contract (LLD 4.2.5)

  • Queue drains oldest-first, metadata rows before video blobs — scores reach the dashboard even if video is still climbing a 2 Mbps link.
  • Chunked upload with byte-range resume; server returns an ETag per chunk, client stores chunk_offset.
  • Exponential backoff: 5 s → 5 min cap, jittered. Never blocks the UI thread.
  • Conflict rule: same athlete + same test assessed on two devices → keep both attempts, server marks the later one duplicate-pending-review. Never silently overwrite.
  • After a confirmed upload the coach may delete local video to reclaim space; the SHA-256 and result stay.

Crash safety

SQLite WAL + write video to a .part file, fsync, atomic rename. On relaunch, orphan .part files are surfaced as "recover this recording?" rather than deleted.

Edge cases the app must survive (LLD 4.2.8 — evaluators will try these)

  • App killed mid-recording → recover the partial file, offer re-record, never lose the earlier tests.
  • Storage full during recording → stop cleanly, warn with free-space number, offer to delete already-synced video.
  • Camera permission denied → explain in one line what breaks and deep-link to settings.
  • Athlete leaves frame / two people in frame → confidence collapses, result is flagged, not silently wrong.
  • Overexposed midday sun or dark hall → pre-flight blocks recording with a fix instruction.
  • Device rotated mid-take → lock orientation for the whole session at capture start.

Rules of engagement while we build

  • Commit early and often — the committee reviews git history, so a single squashed dump looks fabricated.
  • Any footage of a real person: consent form signed before the camera turns on. Under 18 means guardian signature. No exceptions, this is a disqualification rule.
  • Footage lives on our own machines. Not Drive, not Colab, not a shared cloud folder, not "just for a minute".
  • Write the model card and the known-issue in the same commit as the code. Retrofitting docs at the end is where teams lose marks.
  • If a measurement doesn't work, say so in the log and ship the manual fallback. The brief rewards honesty explicitly.
